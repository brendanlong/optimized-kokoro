# Intentional differences from the reference

The Rust port matches the deployed Python pipeline (`reference/`) except for the differences listed here. Each one says what changed, why, how many reference records it changes, and how it was checked (see "Matching the reference vs simplifying it" in `plan.md`).

| Area | Reference behaviour | Ours | Why | Records changed | Checked by |
|---|---|---|---|---|---|
| misaki English | `TypeError` when a punctuation-tagged token starts with `İ` | Returns phonemes | The request shouldn't fail | 0 in corpus (30 of 4,000 random strings) | PR #5 fuzzing |
| espeak-ng: digit grouping | `CheckThousandsGroup` (numbers.c:1457) and `TranslateNumber_1` (numbers.c:1611–1621) read past the end of the clause into `TranslateClauseWithTerminator`'s uninitialised stack arrays, so how a long digit string is grouped depends on digits an earlier clause, or an earlier request, left there. fr `LCCN 91052684` after an ISBN reads "…milliard…millions…" | `sbuf`, `words`, `charix`, `number_buf` and `num_wtab` start each clause zeroed, so the output depends only on the text (`LCCN 91052684` → "quatre-vingt-onze millions cinquante-deux mille six cent quatre-vingt-quatre") | Deterministic output; one request can't change how another reads a number | 1 of 140,344 corpus espeak calls (2 fr-fr wrapper outputs, listed in `crates/espeak/tests/divergences.jsonl`); 15 of 133,931 generated calls | memcheck on C (`oracle.py --ub`); `earlier_text_does_not_change_number_reading` |
| espeak-ng: `$text` replacements | `TranslateWord`'s skip loop (translate.c:191) runs past the end of a replacement with fewer words than the entry skips, reading stack memory; output varies between runs (es `A.$U.A`) | Stops at the end of the text | Undefined behaviour in C | 0 | ASan |
| espeak-ng: other out-of-bounds reads | On some input C reads outside stack buffers, and sometimes segfaults. Examples: `InterpretCondition` (synthdata.c:618) and `CountVowelPosition`/`isAfterStress` walk off the start of phoneme lists; `MatchRule`'s syllable count (dictionary.c:1766) scans past the end of the clause buffer looking for a space, in 19% of es corpus calls | Reads outside a buffer give 0 and the scan stops at the buffer's end; no crash | Undefined behaviour in C | 0 (the port still gives C's answer on all other 1,359 corpus calls and all other 6,085 generated calls where C reads undefined memory) | ASan, memcheck, fuzzing |

Records are `espeak_TextToPhonemes` calls: the corpus dump's calls (misaki/phonemizer on the Gutenberg and Wikipedia corpus, 12 voices) and the generated texts (`gen_adversarial.py` and `gen_dict.py`, all 141 voices), replayed in order with one engine per voice. The oracle flags calls where C reads out of bounds or reads uninitialised memory (`oracle.py pairs --ub`): 1,360 corpus calls and 6,100 generated calls. The parity tests run those calls but don't score them, since C's answer depends on whatever memory it read.

Not changed: state that C keeps between calls by design. An embedded command such as `\x01B` (speak punctuation) or `\x01…Y` (say-as) stays on for every later call, and a character read ahead at the end of one call starts the next. phonemizer keeps one library per language, so the reference carries this from one request to the next, and so does the port. Starting each call with fresh state changes 0 of the corpus calls, but 45% of the adversarial calls on the 12 Kokoro voices and 17% of those on all 141 voices, which are full of embedded commands.
