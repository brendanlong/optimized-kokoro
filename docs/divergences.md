# Intentional differences from the reference

The Rust port matches the deployed Python pipeline (`reference/`) except for the differences listed here. Each one says what changed, why, how many reference records it changes, and how it was checked (see "Matching the reference vs simplifying it" in `plan.md`).

| Area | Reference behaviour | Ours | Why | Records changed | Checked by |
|---|---|---|---|---|---|
| misaki English | `TypeError` when a punctuation-tagged token starts with `İ` | Returns phonemes | The request shouldn't fail | 0 in corpus (30 of 4,000 random strings) | PR #5 fuzzing |
| espeak-ng: state between calls | C keeps its globals from one `espeak_TextToPhonemes` call to the next, and phonemizer keeps one library per language, so one request can change later requests for that language: an embedded `\x01B` turns on spoken punctuation and `\x01…Y` say-as mode for good, and a character read ahead at the end of one call is read at the start of the next | Every `text_to_phonemes` call starts from the state a new library has right after `espeak_SetVoiceByName`; the only thing shared between calls is the immutable loaded data. Restoring that state (copying the small part, clearing the large buffers) costs 1–2 µs per call | Untrusted text in one request must not change another user's output | 0 of 140,344 corpus calls; 45% of the adversarial calls on the 12 Kokoro voices and 17% on all 141 (generated texts are full of embedded commands) | C answers from a child forked after `espeak_SetVoiceByName` for every call (`oracle.py pairs`; `--history` gives the reference's behaviour); `earlier_text_does_not_change_later_calls` |
| espeak-ng: digit grouping | `CheckThousandsGroup` (numbers.c:1457) and `TranslateNumber_1` (numbers.c:1611–1621) read past the end of the clause into `TranslateClauseWithTerminator`'s uninitialised stack arrays, so how a long digit string is grouped depends on digits an earlier clause, or an earlier request, left there. fr `LCCN 91052684` after an ISBN reads "…milliard…millions…" | `sbuf`, `words`, `charix`, `number_buf` and `num_wtab` start each clause zeroed, so the output depends only on the text (`LCCN 91052684` → "quatre-vingt-onze millions cinquante-deux mille six cent quatre-vingt-quatre") | Deterministic output; one request can't change how another reads a number | Against the reference: 1 of 140,344 corpus espeak calls (2 fr-fr wrapper outputs, listed in `crates/espeak/tests/divergences.jsonl`) and 15 of 133,931 generated calls. Against C from fresh state: 0 corpus calls (in a new process those bytes happen to be zero, as here) and 6 generated calls, where an earlier clause of the same text left digits there | memcheck on C (`oracle.py --ub`); `earlier_text_does_not_change_number_reading` |
| espeak-ng: `$text` replacements | `TranslateWord`'s skip loop (translate.c:191) runs past the end of a replacement with fewer words than the entry skips, reading stack memory; output varies between runs (es `A.$U.A`) | Stops at the end of the text | Undefined behaviour in C | 0 | ASan |
| espeak-ng: other out-of-bounds reads | On some input C reads outside stack buffers, and sometimes segfaults. Examples: `InterpretCondition` (synthdata.c:618) and `CountVowelPosition`/`isAfterStress` walk off the start of phoneme lists; `MatchRule`'s syllable count (dictionary.c:1766) scans past the end of the clause buffer looking for a space, in 19% of es corpus calls | Reads outside a buffer give 0 and the scan stops at the buffer's end; no crash | Undefined behaviour in C | 0 (the port still gives C's answer on all other 1,359 corpus calls and all other 6,085 generated calls where C reads undefined memory) | ASan, memcheck, fuzzing |

Records are `espeak_TextToPhonemes` calls: the corpus dump's calls (misaki/phonemizer on the Gutenberg and Wikipedia corpus, 12 voices) and the generated texts (`gen_adversarial.py` and `gen_dict.py`, all 141 voices), compared with C answering each call in order in one process per voice, as the reference does (`oracle.py pairs --history`). The oracle flags calls where C reads out of bounds or reads uninitialised memory (`oracle.py pairs --ub`): 1,360 corpus calls and 6,100 generated calls in the reference's call order, and 1,360 and 4,638 from fresh state. The parity tests run those calls but don't score them, since C's answer depends on whatever memory it read. The parity tests take C's answers from fresh state for every call (`oracle.py pairs`), that is, the reference plus the state-between-calls row.
